# 版本与发布管理

## 当前基线

当前未发布，尚无产品版本号。不要仅因创建管理文档就生成 v0.1.0 或宣称首版完成。

## 版本策略

采用 MAJOR.MINOR.PATCH，Git 标签使用 vMAJOR.MINOR.PATCH。

- 首个可运行且通过约定验收的开发版本可从 0.1.0 开始，由维护者根据实际成熟度确定。
- 0.x 阶段：新增功能或不兼容调整升级 MINOR，兼容修复升级 PATCH；不兼容变更仍须明确记录。
- 1.0.0 及以后：不兼容接口/行为/数据格式变化升级 MAJOR，兼容功能升级 MINOR，兼容修复升级 PATCH。
- 预发布可使用 0.1.0-rc.1 等编号；预发布不等同稳定版。
- 纯文档维护通常进入 Unreleased，随下一次产品版本发布；无需每次提交都升级版本。
- 技术栈确定后，以其包元数据为唯一版本来源；没有合适元数据时再引入 VERSION 文件。避免多处手工维护版本号。

## 发布前检查

- [ ] 确定版本范围、对应 REQ/Issue 和验收状态。
- [ ] main 已包含拟发布的所有合并变更，记录完整提交 SHA。
- [ ] 在该提交上完成相关测试/构建/数值验证，保存命令、环境、结果和限制。
- [ ] 确认公开内容、第三方许可、依赖及生成物符合项目要求。
- [ ] 更新唯一版本来源，并将 Unreleased 中本次内容移到版本及发布日期标题下。
- [ ] 写明已知问题、不兼容变化、迁移方法和回退方案。
- [ ] 完成维护者审阅；发布操作具备明确授权。

## 发布操作

1. 合并版本准备变更，记录最终发布提交 SHA。
2. 针对该确切提交创建不可变的 vX.Y.Z 标签。
3. 创建 GitHub Release，说明版本内容、对应需求、验证结果、已知限制和产物。
4. 产物如适用，提供可追溯来源及校验值；不要发布临时输出或本机环境。
5. 核对 Release、标签、元数据版本和 CHANGELOG 一致。
6. 将需求台账补上实际交付版本和证据；保留新的 Unreleased 段落。

不在本次初始化中启用自动发布。未来自动化应在实际构建和验证流程建立后配置。

## 回退与修复

- 已发布标签不移动、不覆盖；发现问题发布新的补丁或明确标记受影响发布。
- 代码回退优先使用可审阅的 revert 提交，保留历史。
- 必要时指引使用者退回上一已验证版本，并说明数据/格式兼容限制。
- 记录原因、影响范围、修复版本及复验结果。

## Release 说明格式

版本和日期 / 发布提交 SHA / 关联需求 / 新增与修复 / 不兼容变化及迁移 / 验证命令与结果 / 已知问题 / 产物和校验值（如适用）/ 回退说明。
